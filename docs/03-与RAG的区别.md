# 与 RAG 的本质区别:外挂 vs 本体

> **一句话:RAG 解决「怎么取知识」(读侧/机制/外挂,取完不增值);编译复利解决「知识怎么变成资产并增值」(写侧/资产/本体,越用越富)。两者不是竞争——编译过的 wiki 也可以用 RAG 检索,但增值来自编译,不来自检索。**

## 一、为什么「加个向量库检索原文」不够

最常见的疑问:「你的 wiki 检索(混合检索:BM25+向量)不就是 RAG 吗?」

是,也不是。`kcp search` / `search_wiki` 用的是 RAG 的检索机制——**但检索的对象不同**:

| | RAG 外挂知识库 | 知识编译复利(kcp) |
|---|---|---|
| 检索的对象 | 原文碎片(切块+向量化,信息平面) | **思考结果**(结构化页面+交叉引用图+判断沉淀,立体) |
| 存什么 | 文档 chunk,原样 | 论证链 / 意外发现 / 连接+意义 / 矛盾标注 / 置信度 |
| 矛盾处理 | 无——两篇矛盾的文档各取一半喂模型,现场仲裁 | **写时显式标注**,反映到「张力与缺口」 |
| 置信度 | 无——所有片段同等可信 | 单源=low、多源=high,模型知道该多信哪句 |
| 查询性质 | 消耗——答案用完即弃 | **投资**——好答案 filed back 让库更密 |
| 随使用变化 | 不变 | **复利增长** |
| 从错误学习 | 不会 | 会(observe 回灌) |
| edge 在哪 | 在模型的二次加工(平均人) | **在知识库本身**(私有连接前置沉淀) |
| 成本时点 | 读时付费:每次查询 检索+噪声+重推理 | 写时付费:编译蒸馏;查询时信息密度高 |

## 二、四条本质差别

**1. 知识复利 vs 原地踏步**
RAG 语料是死的:加一篇文档只是多一批 chunk,上一轮问答的洞见不会沉淀。kcp 的「查询即投资」闭环(query → filed back 成 synthesis 页)是 RAG **结构上做不到的**——每次使用都在让库更密。

**2. 跨源综合 vs 原子 chunk**
问「这两份资料哪个对」:RAG 给你两块可能互相矛盾的 chunk,让模型每回现场仲裁;编译在写时就完成了跨源综合与矛盾标注。**这是编译时信息,检索时拿不到。**

**3. 写时付费 vs 读时付费**
RAG 索引便宜(切块+embedding),但每问一次付一次检索+推理钱,且单靠向量召回有 60-80% 的天花板。编译贵(一次策展),但每次查询读到的是挤干水分的页面——一句话结论几行顶一整个 chunk。

**4. 错误模式不同**
RAG 错了是「这一次的检索/生成错」,下次问可能就对;编译错了是「概括时固化的错」,会一直留在 wiki 里,需要 lint + review_after 兜底。**编译式系统的风险是错误慢变量,检索式系统的风险是错误快变量。**

## 三、我们也是 RAG——机制复用,对象不同

`kcp` 的检索层本身就是 RAG 的生产基线实现:

- **混合检索**:BM25-lite 词法(精确匹配)+ 可选向量余弦(语义),0.55/0.45 融合
- **离线可跑**:不配 `KCP_EMBED_MODEL` 时用本地字符 n-gram 哈希嵌入(确定性、零依赖)
- **维度护栏**:切换嵌入器时缓存维度校验,防「索引和查询不在同一向量空间」

所以准确的表述是:**kcp 用 RAG 的机制,检索编译过的资产**。增值来自编译,不来自检索——检索只是让编译的成果被高效取回。

## 四、RAG 什么时候仍然是对的

编译不是万灵药,有明显代价(写时人工策展、新资料有编译滞后、规模受人工瓶颈限制)。以下场景 RAG 仍然正确:

| 场景 | 为什么 RAG 对 |
|---|---|
| 语料巨大(几十万文档)、无人工 | 编译的人力成本不可行 |
| 内容频繁变化(实时数据/每日新闻) | 编译滞后,换资料即时生效 |
| 一次性资料(分析一份长合同) | 直接放上下文/检索,不值得沉淀 |
| 事实精确查询(运单号/错误码) | RAG 词法检索够用,编译收益小 |

**决策框架**:语料小、复读率高、要复利 → 编译;语料大、变化快、一次性 → RAG。企业知识库(规范/复盘/决策)通常落在编译一侧——因为这类内容**复读率高且值得沉淀**。

## 五、对照实验证据(可复现:`kcp eval`)

「本质不同」不是口号,已自动化成对照实验:

1. 同一批语料,评估种子 `eval/seeds/*.json`(问题 + 期望要点)
2. 路线 A(RAG 外挂):直接检索 `raw/` 原文碎片答题
3. 路线 B(编译复利):检索编译后的 `wiki/` 资产答题
4. Agent-as-a-Judge 按 5 维打分(论证完整性/连接价值/矛盾标注/综合密度/可迁移性),报告落 `eval/reports/`

实测(2026-10-03, GLM-4.5-air, demo 语料):**B 优 3/3,均分 RAG 3.3 vs 编译 4.4(+1.1)**——连接价值/综合密度差距最大:编译复利在需要综合与迁移的问题上优势显著,纯事实检索差异小。随语料复杂度放大,差距会拉大。

> 在你自己知识库上跑一遍:`KCP_API_KEY=... ./kcp eval --seeds eval/seeds/knowledge-base.json`

## 六、结论

```
RAG        = 取知识的机制(读侧,每次查询临时拼装,取完不增值)
知识编译    = 让知识成为资产的机制(写侧,编译/查询投资/失败回灌,越用越富)
```

**RAG 给 Agent 碎片,编译给 Agent 员工手册。** 谁都想让自己的 agent「第一次就做对」——手册让这件事成为可能,而手册只能通过编译沉淀出来。
