# 运行原理:知识怎么被编译、增值、并被 agent 消费

> 一句话:这是一个「知识编译器」——把散落的原始资料(raw)编译成结构化、交叉链接、带矛盾标注与置信度的私有知识资产(wiki),再通过两种方式喂给 agent(你自己跑的角色、以及通过 MCP 喂给 Claude Code/Codex/自定义 agent)。**编译发生在写时,消费发生在读时。**

## 一、三层架构

```
Layer 3: SCHEMA.md         编译纪律(页面格式约定)——本项目的心智,决定「编译成什么样」
Layer 2: wiki/             编译产物(你的知识资产,可导出、可带走)
Layer 1: raw/              不可变源文件(文章、论文、剪藏、观察) = 事实来源
```

- `raw/` 是源代码,**不可变**——你永远不修改它
- `wiki/` 是编译产物,由 compiler agent 写入,分五类:
  - `wiki/sources/` — 每个 raw 源的摘要页(1:1 映射),含完整论证链
  - `wiki/concepts/` — 概念页(跨源综合、矛盾标注、置信度分层)
  - `wiki/entities/` — 实体页(人物、工具、项目、组织;2+ 源提及才建)
  - `wiki/synthesis/` — 综合文档(从 query 中 filed back 的永久分析)
  - `wiki/notes/` — 低置信度工作笔记(外部工具写入,事后可升级)

## 二、编译管线(写时)

```
raw 文件
  │  kcp compile <raw文件>
  ↓
compiler agent(自研,按 SCHEMA.md 执行)
  ├─ 1. 读全文
  ├─ 2. 判断 origin(external 他人资料 / self 自己实践)
  ├─ 3. 写 wiki/sources/ 源摘要页(论证链完整性:SQL/代码/对比表/示例逐字保留)
  ├─ 4. 创建/更新 concept / entity 页(跨源综合 →「外部观点」+「我的实践」分流)
  ├─ 5. 标注矛盾(新源与已有页冲突时,两边保留并显式标注)
  ├─ 6. 添加 [[wikilinks]] 交叉引用(通常触及 5-15 个已有页)
  └─ 7. 策展决策点暂停:概念页该不该建?由你在终端裁决
```

**质量是可验收的**,不是「AI 写了一段」:
- `kcp preflight <raw>` — 硬资产完整性核验:每个代码块/表/示例是否出现在 source 页对应位置
- `kcp lint` — 断链/孤儿/矛盾/过时/未编译源/格式
- `kcp check-sources` — 概念页 sources 是否被错误替换
- `kcp eval` — 编译 vs RAG 对照实验(见下)

## 三、复利闭环(读时 → 写时)

```
执行/编程/决策(你自己,或你的 agent)
   │  ←── 支柱 B:wiki 通过 MCP 按需注入上下文
   ↓
踩坑/失败/新模式/解决方案
   │  ←── kcp observe 捕获
   ↓
raw/observations/
   │  ←── kcp compile 编译回灌(支柱 A)
   ↓
wiki 更密(新源页/概念更新/综合沉淀/矛盾标注)
   ↓
(下次执行读到更丰富的知识 → 回到顶部)
```

**复利的两条腿**:
1. **查询即投资**:`kcp query` 的好答案建议 filed back 成 `wiki/synthesis/` 永久页——每次查询都在让库更密,不是消耗
2. **失败回灌**:踩坑/异常先 `kcp observe` 记下来,再编译入库——下次 agent 直接带着坑的知识工作

这两条腿让「结构密度」随使用次数**增长**,而不是线性堆积——这是复利,不是积累。

## 四、两个支柱 + 一条闭环

```
支柱 A: compiler(写)   raw → 编译进 wiki(自主 agent,SCHEMA 驱动)
支柱 B: context(读)    wiki → MCP server → coding/trading/自定义 agents 当外脑
闭环:   observe         踩坑/失败 → raw/observations → 编译回灌 → wiki 更密
```

- **支柱 B 的关键纪律**:上下文是工作台,不是仓库。wiki **不**全塞进 system prompt——agent 需要时才调用 `search_wiki` / `get_page` 按需取回,控制长上下文稀释与成本。
- **为什么值得喂给 agent**:agent 的能力 = 模型参数记忆(skill/通用常识)+ **你的私有知识**(公司规范、事故复盘、策略规则)。后者模型肚子里没有,只有你自己沉淀——这正是知识库存在的理由。

## 五、自研 agent(全 Go,任意 LLM)

项目自带一个最小自研 agent 运行时(`cmd/kcp` + `internal/`),对应 M04 五组件:

```
Agent = LLM(决策器) + Tools(感知行动) + State(状态) + Loop(循环) + Stop(停止)
  ├─ LLM      internal/provider   OpenAI 兼容 / Anthropic 抽象(KCP_PROVIDER 一换模型全换)
  ├─ Tools    internal/tools      全 Go 工具:wiki 状态/检索/读写文件/lint
  ├─ State    checkpoint 持久化(断点续跑)+ wiki 本身作为长记忆
  ├─ Loop     Think-Act-Observe 循环(工具结果作为观察回填)
  └─ Stop     MaxSteps + MaxSameAction + MaxTokens + Deadline
```

三个内置角色:compiler(编译)、query(检索+综合+filed back 建议)、qa(健康检查)。

## 六、零 LLM 可跑 vs 需要 LLM

| 命令 | 需要 API key? | 说明 |
|---|---|---|
| `kcp status` | ❌ | 页面计数 + 未编译 raw |
| `kcp lint` | ❌ | 健康检查 |
| `kcp search "<查询>"` | ❌ | 混合检索诊断(词法 + 离线字符哈希向量),带 [A]/[B]/[C] 私有度徽标 |
| `kcp list` / `kcp skeleton` / `kcp index` / `kcp update` | ❌ | 确定性操作 |
| `kcp mcp` | ❌ | MCP server 的检索类工具(搜索/读页/相关/最近) |
| `kcp compile` / `kcp query` / `kcp eval` / `kcp mcp`(synthesize_for) | ✅ | LLM 综合/编译/打分 |

配 `KCP_EMBED_MODEL` 后检索升级为语义向量;留空则用本地字符 n-gram 哈希嵌入(离线、零依赖、确定性)。

## 七、一个知识的完整生命周期(例子)

1. 你读到一篇讲 Go channel 泄漏的文章 → 放进 `raw/`
2. `kcp compile raw/go-channel-三铁律.md` → compiler 写成 `wiki/sources/` 源页 + 建/更新概念页
3. 你修一个线上 bug 时踩坑 → `kcp observe -s coding -T "channel 泄漏" -c "..."` → 进 `raw/observations/`
4. 下次 `kcp compile` 把观察回灌 → 概念页「我的实践」更新
5. Claude Code / Codex 写代码时通过 MCP 调 `search_wiki` → 命中「channel 三铁律 + 你的踩坑记录」→ 不重犯
6. 你在 `kcp query` 里问「Go 并发常见坑?」→ 答案 filed back 成 synthesis → 库更密

每一步都让「结构密度」增加——这就是复利引擎的运转方式。
