# 循环设计:知识复利怎么运转

## 核心循环

```
执行/编程/决策
   │  ←── MCP 注入 wiki 上下文(支柱 B)
   ↓
踩坑/失败/新模式/解决方案
   │  ←── observe 捕获
   ↓
raw/observations/
   │  ←── compiler 编译回灌(支柱 A)
   ↓
wiki 更密(新源页/概念更新/综合沉淀/矛盾标注)
   │  ←── 下次执行读更丰富的知识
   ↓
(回到顶部)
```

**复利的两条腿**:查询即投资(每次好 query filed back)+ 失败回灌(每次踩坑编译入库)。两者都让"结构密度"随使用次数增长——这是复利,不是线性积累。

## 与 RAG 外挂知识库的本质区别

| 维度 | RAG 外挂知识库 | 知识编译复利 |
|---|---|---|
| 库的本质 | 检索语料(chunk+embedding,信息平面) | 知识资产(结构化页面+交叉引用图+判断沉淀,立体) |
| 存什么 | 原文碎片 | 思考结果:论证链/意外发现/连接+意义/矛盾/置信度 |
| 矛盾处理 | 无,各取一半喂模型 | 显式标注,反映到「张力与缺口」 |
| 置信度 | 无,所有片段同等可信 | 单源=low、多源=high |
| 查询性质 | 消耗,答案用完即弃 | 投资,filed back 让库更密 |
| 随使用变化 | 不变 | 复利增长 |
| 从错误学习 | 不会 | 会(observe 回灌) |
| edge 在哪 | 在模型的二次加工(平均人) | 在知识库本身(私有连接前置沉淀) |

一句话:**RAG 解决"怎么取"(读侧/机制/外挂),编译复利解决"知识怎么变成资产并增值"(写侧/资产/本体)。** 两者不是竞争——编译过的 wiki 也可以走 RAG 检索,但增值来自编译,不来自检索。

## 质量如何保证

编译纪律(SCHEMA)把"知识库是 agent 的燃料"这件事做成可验收的:

1. **论证链完整性核验**:每个 SQL/代码/对比表/示例是否都在 source 页对应位置出现,缺则补
2. **lint 健康检查**:断链/孤儿/矛盾/过时/未编译源/格式
3. **置信度分层**:单源 = low,多源 = high——agent 知道该多信哪句
4. **意外发现必填**:每个源摘要至少一行你自己的分析——纯搬运不产生 edge

## 对照实验(已自动化:`kcp eval`)

"编译 vs RAG"的差异主张要从信念变成证据——`kcp eval`(Phase 4)已把下面的手工流程自动化:

1. 同一批语料:评估种子 `eval/seeds/*.json`(问题 + 期望要点,需按自己的知识库改写)
2. 路线 A(RAG 外挂):直接检索 `raw/` 原文碎片,LLM 答题
3. 路线 B(编译复利):检索编译后的 `wiki/` 知识资产,LLM 答题
4. Agent-as-a-Judge 按 5 维打分(论证完整性/连接价值/矛盾标注/综合密度/可迁移性),报告落 `eval/reports/`

实测(2026-10-03, GLM-4.5-air, demo 语料):B 优 3/3,均分 RAG 3.3 vs 编译 4.4(+1.1),连接价值/综合密度差距最大——编译复利在需要综合与迁移的问题上优势显著,纯事实检索差异小。这也说明"本质不同"是可测量的,且随语料复杂度放大。
